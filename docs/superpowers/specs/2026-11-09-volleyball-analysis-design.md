# バレーボール記録・分析アプリ 設計書

作成日: 2026-11-09
依頼者: 猪原さん（チームの監督・コーチの立場で使う）

## 1. 目的と背景

部の生徒が練習試合・公式戦を見ながらタブレットやPCで記録し、監督はその内容をリアルタイムに見ながら、選手の調子と状況に合わせて選手交代や作戦を判断できるようにする。試合後には詳細データ（レシーブ判定など）を追加入力し、決定率などを自動計算して戦略づくりに使う。

成功の姿:
- 記録係の生徒が試合のスピードに遅れずに入力できる（1プレー3タップ程度）
- 監督が別の端末で「今、誰の調子が悪いか」「相手の前衛は誰か」をひと目で判断できる
- 試合後・複数試合を通して、選手別・ローテ別・相手別の数字で振り返れる

## 2. 目標 / 対象外 / やってはいけないこと

目標:
- 自チーム・相手チームの選手登録
- 試合中のリアルタイム記録（得点・失点・誰が・何で・どこから）
- 自チーム・相手チーム両方のローテーション表示と自動ローテ
- 選手交代（リベロ含む）の記録
- 別端末へのリアルタイム共有
- 試合後のレシーブ判定（A〜D）入力
- 分析画面（選手別・ローテ別・相手別、試合単体と通算）

対象外（今回は作らない）:
- 動画の取り込み・再生との連動
- トス・ディグ・ブロックタッチなど、全プレーを細かく記録するスカウティング（DataVolley級）
- 複数チーム（他校）が使うサービスとしての運用

やってはいけないこと（技術的に動いても失敗とみなす）:
- 試合中の入力が遅い・迷う（ボタンが小さい、確認ダイアログが多い、画面遷移が多い）
- 電波が一瞬切れたら入力が消える
- 生徒の名前などが合言葉なしで誰でも見られる

## 3. 動作環境・作り方（本人の決定）

- 端末: タブレット（横向きがメイン）とPC。
- 会場ではネット接続がある前提。

以下は設計者（Claude）の判断:
- ブラウザで動くWebアプリ（PWA）。インストール不要、ホーム画面への追加は可能。
- 技術構成は既存のダーツ記録アプリと同じ Vite + Preact + TypeScript に合わせる。
- リアルタイム共有とデータ保存は Firebase（Cloud Firestore、無料枠）。オフライン一時保存（Firestore のオフライン永続化）を有効にし、切断中の入力は再接続時に送る。
- 公開は GitHub Pages（個人アカウント taiki-iha、ダーツアプリと同じ運用）。ソースのリポジトリに選手名などのデータは置かない。データは Firestore だけに保存する。
- アクセス制限: チームごとに「チームコード（合言葉）」を設ける。最初にチームコードを入力した端末だけが、そのチームのデータを読み書きできる（Firebase 匿名認証とチーム参加記録を組み合わせ、Firestore のセキュリティルールで制限する）。生徒がGoogleアカウントを持っていなくても使えるようにするため。
- 生徒の名前を Firebase に保存することは本人が了承済み（2026-11-09）。Firebase プロジェクトは本人の個人Googleアカウントで作成する。
- 想定するチームは1つ（自チーム）。ただし、データ構造はチーム単位で分けておく。

## 4. 画面と機能

### 4.1 選手登録
- 自チーム: 背番号、名前、ポジション（S/OH/MB/OP/L）。
- 相手チーム: チーム名、背番号、ポジション（名前は任意）。登録した相手チームは、次の対戦で再利用できる。
- 相手のポジションは試合中に分かることも多いので、試合中にも追加・変更できるようにする。

### 4.2 試合の作成
- 種別（練習試合 / 公式戦）、日付、相手チーム、大会名（任意）。
- 試合形式: 何セットマッチか（3セット・5セット・セット数固定の練習試合）、1セットの点数（25点、最終セットは15点）。デュースあり。セット数固定の練習試合では、勝敗が決まっても全セットを行う。
- 各セットの開始時に、両チームのスタメン6人の配置（ポジション1〜6）と、最初のサーブ権を入力する。リベロの登録もここで行う。

### 4.3 試合中の入力画面（コート型 A案。本人がモックアップから選んだ）
レイアウト（タブレット横向き）:
- 上: 点数、セット数、セットカウント、サーブ権、自チームと相手の現在のローテ番号。
- 中央: コートを両チームぶん表示（ネットを挟んで向かい合う形）。各ポジションに背番号と役割を表示する。
- 横: 「選択中の選手 → プレーボタン」、選手ごとの今日の成績（調子）、選手交代ボタン、タイムアウト記録ボタン、「1つ戻す」ボタン。

記録の流れ（1ラリー）:
1. コート上の選手（自チームまたは相手）をタップ
2. プレーを選ぶ: スパイク決定 / スパイクミス / サーブエース / サーブミス / ブロック得点 / その他の得点 / その他のミス
3. 打った位置のゾーン（1〜6）をタップ（サーブ系は省略可）
→ 点数・サーブ権・ローテが自動で更新される。

- 「相手のミスで得点」のように選手を特定しない得点・失点用に、選手を選ばずに押せるボタンも用意する。
- スパイク打数: 決まらなかったがラリーが続いたスパイクも数えたいので、「スパイク（継続）」ボタンで打数だけ加算できるようにする。点数は動かない。
- ローテーション: サイドアウトでサーブ権を得たチームが時計回りに1つ回る。
- 「1つ戻す」で、直前の記録（点数・ローテの変化を含む）を取り消す。
- 確認ダイアログは出さない。間違いは「1つ戻す」で直す。

選手交代:
- 交代ボタン → コートの選手をタップ → ベンチの選手をタップ、で入れ替わる。交代回数（1セット6回まで）を表示する。上限を超える場合は警告のみ出し、操作は止めない（練習試合ではルールが違うことがあるため）。
- リベロ: 後衛の選手と入れ替える操作を用意する。前衛に回ったリベロには注意を表示する。リベロの入れ替えは交代回数に数えない。
- 相手チームの交代も同じ操作で記録する。

調子の表示:
- 選手ごとに「スパイク決定数/打数」「サーブミス数」を今日の試合分で表示する。
- 調子が悪い選手はコート上の表示色を変える。初期の基準は「スパイク5本以上で決定率30%未満」または「そのセットのサーブミス2本以上」。基準は設定画面で変えられるようにする。

### 4.4 監督用の閲覧（リアルタイム共有）
- 同じ試合を開いた別の端末に、入力内容が1秒程度で反映される。
- 閲覧専用モード（入力ボタンを隠し、コート・点数・調子・相手ローテを大きく表示）を用意する。監督の端末からでも入力はできる（モード切替）。
- 同時に入力するのは1台だけを想定する。2台で同時に入力したときの競合処理は、最後に書いた方を優先する簡単な方式でよい。

### 4.5 試合後の詳細入力（レシーブ判定）
- 相手のサーブを1本ずつ時系列で一覧にする（どのセット・何点目・相手サーバー・その時の自チームのローテを試合中の記録から自動で付ける）。
- 1本ごとに「誰がレシーブしたか」と「判定A〜D」を入力する。動画を見ながら順番に入れることを想定し、入力したら次の行へ自動で移る。
- 判定の定義（設計者の判断。画面にも表示する）:
  - A: セッターが動かずにトスでき、どの攻撃も使える返球
  - B: セッターが少し動く。攻撃の選択肢がやや減る
  - C: セッターが大きく動く、または二段トス。速攻は使えない
  - D: 返球できない（サービスエースを取られた、またはダイレクトで相手コートに返った）
- サーブエースを取られた行は、最初から D として入っている（レシーブした選手だけ入力する）。
- 試合中にレシーブ判定を入れる操作は必須にしない（試合中の入力を増やさないため）。

### 4.6 分析画面
試合単体と、期間や種別（練習試合/公式戦）で絞り込んだ通算の両方を見られるようにする。

選手別:
- スパイク: 打数、決定数、ミス数、決定率（決定÷打数）、効果率（(決定−ミス)÷打数）、ゾーン別の決定数
- サーブ: 本数、エース数、ミス数、ミス率
- ブロック得点数
- レシーブ: 本数、A/B/C/D の本数、返球率（(A+B)÷全体）、Aパス率

ローテ別（自チームのローテ1〜6）:
- そのローテでの得点・失点、サイドアウト率、ブレイク率

相手チーム:
- 相手選手別の得点（何番がどのゾーンから何本決めたか）
- 相手サーバー別の自チームのレシーブ成績（誰のサーブで崩れるか）
- 相手のスタメン配置とローテの記録（次の対戦のために残す）

表示は表とシンプルなグラフ。CSV出力ができると良い（優先度は低い）。

### 4.7 細かい取り決め（設計者の判断）
- **ローテ番号**: セッター基準（S1〜S6。セッターがポジション1にいるときがS1）。セッターは各セット開始時に指定する（ポジションSの選手を初期値にする）。セッターが交代したら、入った選手を新しいセッターとして扱う。セットや試合をまたいでもローテ別成績を比べられるようにするため。相手チームも同じ考え方で、相手セッターを指定できれば S 番号を出す（不明なら開始順の番号）。
- **被ブロック**: 自チーム選手のプレーに「スパイク被ブロック」を用意する（失点。打数とミスに数える）。ブロックした相手選手は任意で追加タップできる。相手選手の「ブロック得点」から入力した場合は、自チーム打者は不明扱いになる。正確な効果率のためには自チーム側から入れることを画面上で案内する。
- **ゾーンの意味**: スパイクは「打った位置」（前衛 4/3/2、バックアタックは 5/6/1）。サーブは任意で「落ちた位置」。
- **過去の記録の修正**: 試合中は「1つ戻す」のみ。試合後にイベント一覧から、選手・プレー・ゾーンを書き換える画面を用意する（点数が変わるような修正は対象外）。点数・成績はイベントから計算し直すので、修正はそのまま反映される。
- **チームコードの運用**: チームを作った端末（監督）が管理者。管理者はチームコードを変更でき、変更すると他の端末は新しいコードを入れ直すまで使えなくなる（卒業生などの締め出し用）。試合・選手の削除は管理者だけができる。それ以外の役割の区別はしない。

## 5. データ（概要）
- チーム、選手、相手チーム、相手選手
- 試合 → セット → イベント（得点・失点・プレー・交代・タイムアウト・ローテ状態）
- イベントは時系列で追加していく形式にし、点数・ローテ・成績はイベントから計算する（「1つ戻す」や後からの修正に強くするため）。
- レシーブ判定は、相手サーブのイベントにひも付けて後から追加する。

## 6. 設計者に任せること
- 画面の細かいデザイン、色、フォント
- Firestore のデータ構造の詳細とセキュリティルールの書き方
- グラフの種類
- 公式ルールの細部（デュースの扱いなど）は一般的な6人制ルールに合わせる

## 7. 設計者の判断で決めた点（本人の確認待ち）
- Firebase と GitHub Pages を使うこと、ダーツアプリと同じ技術構成にすること
- チームコード（合言葉）方式のアクセス制限
- レシーブ判定 A〜D の定義
- 調子が悪いとみなす初期基準
- 交代回数の上限は警告のみで、操作は止めないこと
- 「1つ戻す」ボタンを用意し、確認ダイアログは出さないこと
- 4.7 の取り決め全部（ローテ番号、被ブロック、ゾーン、修正画面、チームコード運用）
